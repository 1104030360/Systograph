為什麼用 Modular RAG 當共同架構？

因為 Modular RAG 的重點是「模組邊界」，不是某條固定 pipeline。 它可以向下表示 naive RAG 的最小流程，也可以向上承載 planner、router、agent loop、tool calling、memory、GraphRAG、多模態與 governance。

Filter 的產品意義

同一張圖不應該只有一種閱讀方式。工程師看 data flow，PM 看能力覆蓋，安全 reviewer 看 policy gate， SRE 看 trace、latency、cost，研究者看 variant 如何接到共同 backbone。

輸入任意系統時的流程

  1. 讀取 code、config、workflow JSON、trace 或文件。
  2. 抽出 LLM、tool、retriever、memory、guardrail、eval 等原始元件。
  3. 正規化成共同 node / edge schema。
  4. 依 layer、capability、contract、risk、metrics 分類。
  5. 渲染成可篩選、可檢查、可追 trace 的 canvas。

前端已能表達，後端仍要補強

這個頁面現在把 schema-driven graph 需要的視角都放進 UI；但真正 input 任意 AI agent system，需要後端 mapper 產生這些欄位，前端才有可信資料可畫。

Frontend projection now

  • 標準節點、擴充子系統、未映射元件可分開看。
  • Extension node 可在 inspector 展開內部 pipeline。
  • Reasoning mode 與 deployment topology 已有視角。
  • 每個 node 可顯示 source mapping evidence。

Backend mapper still needed

  • Code/config/workflow/trace/doc importer adapters。
  • Known-node classifier 與 extension-system detector。
  • Unknown-safe mapper：無法分類時放入 unmapped_components。
  • Subgraph extractor：把 RAG-Anything、Infini Memory 類系統拆成內部 pipeline。
  • Source mapping generator：每個 node 回指 code path、config key、trace span 或 doc section。
