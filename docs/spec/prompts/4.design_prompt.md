## 核心實體（from erm.dbml）
1. **Ticket** - 工單實體（含 AI 分析結果與風險評分）
2. **WeightConfiguration** - 風險評分權重配置
3. **FieldPriorityConfiguration** - Excel 欄位讀取優先順序配置
4. **SentenceDatabase** - 語句資料庫（高風險關鍵字、升級觸發詞）
5. **GPTPromptConfiguration** - AI 模型提示詞配置
6. **SyncPathConfiguration** - SharePoint/OneDrive 同步路徑配置
7. **ChatSession** - RAG 對話會話
8. **CategoryMemory** - AI 分類記憶（保持分類一致性）
9. **UploadedFile** - 上傳檔案記錄
10. **FAISS 向量索引** - 384 維向量檢索引擎（all-MiniLM-L6-v2）

## 核心功能（from features/）
1. **工單上傳** - Excel (.xlsx) 檔案上傳與預覽（10MB 限制，重複檢測）
2. **RAG 對話查詢** - 自然語言查詢歷史工單（SQL/Semantic/Hybrid/Followup 四類代理）
3. **風險評分** - 基於關鍵字/頻率/影響的智慧評分（0-100 分，四級風險分類）
4. **知識庫同步** - Excel ↔ SQLite ↔ FAISS 三向同步（增量更新，衝突解決）
5. **工單聚類** - KMeans/HDBSCAN 聚類分析與 LLM 自動命名
6. **問題摘要提取** - AI 生成 ≤50 字問題摘要
7. **解決方案提取** - 從工單描述中提取解決方案
8. **對話會話管理** - 多輪對話記錄儲存與載入
9. **系統配置管理** - 權重/優先順序/提示詞的動態配置

## 當前技術棧（已實作）
- **後端框架**: Flask 3.1.0
- **資料庫**: SQLite3 (resultDB.db)
- **向量檢索**: FAISS (IndexFlatL2 + IndexIDMap, 384維 all-MiniLM-L6-v2)
- **AI/ML**:
  - AutoGen 0.9.2 (多代理編排)
  - Sentence Transformers (paraphrase-MiniLM-L6-v2用於風險評分, all-MiniLM-L6-v2用於FAISS索引)
  - Cross-Encoder (ms-marco-MiniLM-L-6-v2用於重排序)
  - spaCy (中文分詞)
  - KeyBERT (關鍵字提取)
- **LLM 整合**:
  - Power Automate AI Builder (主要雲端服務,最多50並發)
  - Ollama (本地 fallback: llama3.2, deepseek-coder-v2, command-r7b, phi3, orca2)
- **Excel 處理**: win32com (Windows COM 自動化)
- **前端**: Jinja2 + Bootstrap 5 + jQuery + DataTables

# 任務目標

請以 **Linus Torvalds 的工程哲學**來規劃與設計系統重構或擴展方案：

## Linus 工程原則
1. **簡單直接** - 避免過度設計，選擇最簡單能用的解決方案
2. **務實優先** - 先讓系統能動，再優化細節
3. **明確邊界** - 清楚定義每個模組的責任與介面
4. **漸進演化** - 支持未來擴展，但不預先實作用不到的功能
5. **效能實在** - 關注實際瓶頸，不做無謂優化
6. **可測性** - 設計要讓測試容易執行

## 設計要求

### 3. 關鍵設計決策
需要在設計文件中明確回答：

#### 資料同步（已釐清）
- **Excel ↔ SQLite ↔ FAISS 同步時機**:
  - 觸發方式: 手動觸發(透過知識庫建構功能)
  - 增量 vs 全量: **全量重建FAISS**(已釐清),SQLite使用analysisTime做增量
  - 衝突解決: **SQLite為準**(已釐清),Excel僅作初始匯入與匯出
  - 備份策略: **僅保留最近1個備份**(已釐清),同步前自動刪除舊備份
  - FAISS模型變更: 需完整重建索引,不支援多版本共存(已釐清)

#### RAG 系統（部分已釐清）
- **LLM Fallback Chain**:
  - Power Automate 失敗後: 自動切換Ollama (llama3.2 → deepseek-coder-v2 → command-r7b → phi3 → orca2)
  - **SQL重試策略**: 所有錯誤類型均重試5次(已釐清)
  - Streaming response: 當前不支援,可考慮未來優化
- **Agent 協作**:
  - Query Classifier: 使用AI Builder分類為SQL/Semantic/Hybrid/Followup
  - **Top-k動態調整**: AI Builder判斷複雜度(具體30/模糊40/摘要50)(已釐清)
  - **Cross-Encoder重排序**: 使用ms-marco-MiniLM-L-6-v2模型(已釐清)
  - Context管理: 對話歷史最多10輪,無大小限制(已釐清)
  - **端到端時間**: <10秒(僅AI推理時間,不含FAISS檢索)(已釐清)

#### 風險評分（已釐清）
- **動態聚類 vs 固定門檻**:
  - **當前邏輯**(已釐清): 資料量≥4 且 範圍>5.0 且 標準差>3.0(三條件AND) → KMeans(K=4固定)
  - **固定門檻**(已釐清): 高風險[70,100], 中風險[50,70), 低風險[30,50), 忽略[0,30)(左閉右開)
  - **語意相似度閾值**: 固定0.7不可調整(已釐清,硬編碼於SmartScoring.py)
  - **權重驗證**: 雙重驗證(前端即時+後端儲存)(已釐清)
  - **可操作性驗證**: 使用AI語意相似度(閾值0.5),與25個樣板比對,無固定黑名單(已釐清)

#### 檔案處理（已釐清）
- **並發上傳**:
  - **Power Automate並發限制**: 50(已釐清,PA_MAX_CONCURRENCY固定值)
  - 多使用者上傳: 當前無佇列機制,可考慮未來實作
  - 是否需要任務佇列: Phase 3可選實作(Celery/RQ)
- **大檔案處理**:
  - **檔案大小限制**: 10MiB (10485760 bytes,使用1024進位)(已釐清)
  - **檔案格式**: 僅接受.xlsx
  - **檔案預覽**: 動態顯示所有Excel欄位,前10筆(已釐清)
  - **重複檢測**: 工單ID重複率≥80%判定為重複(已釐清)
  - **時間戳精確度**: 秒級,同一秒上傳會覆蓋(已釐清)

#### 錯誤處理
- **統一錯誤格式**:
  ```json
  {
    "error": {
      "code": "TICKET_UPLOAD_FAILED",
      "message": "檔案格式不正確",
      "details": {...}
    }
  }
  ```
- **重試機制**: SQL 生成最多重試 5 次，其他操作呢？

#### 測試策略（部分已規格化）
- **單元測試範圍**:
  - Services 層必須有測試(風險評分、RAG查詢、知識庫同步)
  - Repositories 層測試策略(in-memory SQLite)
  - **單筆處理平均時間**: <5秒(已釐清,序列處理不含批次並行)
- **整合測試範圍**:
  - RAG 多代理協作測試
  - 知識庫同步流程測試
  - **召回率測試集**: 100組人工標註查詢與相關工單(已釐清)
  - **召回率目標**: ≥95%(前20筆)(已釐清)
- **Mock 策略**:
  - Power Automate API: 使用requests-mock
  - Ollama 服務: 使用responses
  - FAISS 索引: in-memory或fixture

#### 跨平台支援

  - 替代方案：openpyxl + pandas？
  - Excel 檔案鎖定檢測如何跨平台？

# 設計原則檢查清單

在完成設計文件前，請確認是否符合 Linus 原則：

- [ ] **簡單性**: 架構是否足夠簡單？有沒有過度設計？（避免引入不必要的複雜度）
- [ ] **務實性**: 技術選型是否務實可行？保持 Flask/SQLite/FAISS 還是換成更重的方案？
- [ ] **明確性**: 每個模組的責任是否清晰？Services vs Repositories 的邊界？
- [ ] **可演化**: 設計是否支持未來擴展？但沒有預先實作用不到的功能（例如微服務、K8s）
- [ ] **效能**: 是否識別了實際瓶頸？（FAISS 重建、LLM 呼叫、Excel 處理）
- [ ] **可測性**: 設計是否容易測試？依賴注入是否完善？Mock 策略是否清晰？
- [ ] **符合規格**: 設計是否完整覆蓋了所有 9 個 feature files 中的功能？
- [ ] **資料一致性**: Excel ↔ SQLite ↔ FAISS 三向同步的一致性保證？
- [ ] **向後相容**: 重構後是否保持資料庫 schema 相容？配置檔案格式相容？
- [ ] **可觀測性**: 如何監控 LLM fallback chain？如何追蹤 RAG 查詢流程？

# 附錄：當前系統關鍵指標

## 效能指標（需驗證）
- 檔案上傳處理時間：100 筆工單約 1-2 分鐘（含 AI 分析）
- RAG 查詢回應時間：3-8 秒（視 LLM 回應速度）
- FAISS 索引重建：1000 筆約 30-60 秒
- 首次啟動時間：約 10 秒（模型 warmup）

## 資料規模（需確認）
- 工單數量：預估 1K-10K 筆
- FAISS 索引大小：384 維 × 1000 筆 ≈ 1.5MB
- 對話記錄：每個會話平均 5-10 輪

## 使用情境
- 內部工具，預期同時使用者 < 10 人
- 主要操作：上傳分析（低頻）、RAG 查詢（高頻）
- 部署環境：Windows Server 或本機

## 已知問題與待實作功能
### 技術債
1. Analysis.py 過於龐大（2615 行），維護困難
2. 無自動化測試，回歸測試成本高
3. win32com 限制跨平台部署
4. 並發上傳無佇列機制，可能衝突
5. 錯誤訊息不統一，除錯困難
6. 語意 cache 在啟動時全部清空（**已釐清為設計決策**,Analysis.py:121-135)

3. **召回率測試集**: 建立100組人工標註測試集(已釐清)
4. **群集名稱截斷**: 限制30字,超過加"..."(已釐清)
