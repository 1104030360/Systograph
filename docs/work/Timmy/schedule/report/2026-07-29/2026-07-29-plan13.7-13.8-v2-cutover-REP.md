## 一、實作邏輯

### Plan 13.7 — 元件對位 52 格：兩張表變一張、Python dict 變 TOML

**問題（資料結構觀點）**：「元件 → 52 格 reference catalog」有兩條查表路徑——
表A `_TYPE_TO_NODES`（canonical_type 查表，bridge 的 9 種 kind 只有 1 種命中，幾乎死表）
與表B `_LEGACY_SLOT_TO_NODES`（rag-core-v1 legacy slot 查表，實際扛著點亮工作，
但綁死 legacy 模板字彙，UA 接入後即失效）。

**解法**：補齊表A字彙（bridge 9 條＋v1 相容 3 條，合計 39 條）→ 刪除表B與
`_component_nodes()` 的 legacy_slot 分支 → 表A搬進
`core/rules/capability_type_node_map.toml` 成為唯一真相源，由新 loader
fail-closed 載入（value 必須 ∈ catalog 52 node ids、空表/畸形報錯）→
三層護欄防字彙再漂移：
1. **39 條全量 value snapshot**（TOML 任一條被刪或被改指到錯誤節點即紅）
2. **bridge kind 覆蓋護欄**（新增 bridge 規則忘補字彙即紅）
3. **端到端基線**（`basic_qdrant_ollama_rag` 釘住 4 格：`index_builder`/`api_server`/`dense_retriever`=detected、`llm_answerer`=partial——partial 是五態契約的正確期望，間接證據上限就是 partial）

**行為不變性**：拆表B前後真實 fixture 點亮集合完全一致（4/52）；v1 相容路徑
維持原 6 格＋`prompt_builder`（G5b 修復的預期新增）。

### Plan 13.8 — Relationship 閘門：先堵假陽性、再開唯一正當的 alias

**問題**：(1) `_relationship_evidence()` 只用關係名查邊、完全不驗端點——任何
同名邊（不管掛在哪兩個元件上）都能滿足卡片的 relationship gate，alias 機制一開
就是假陽性製造機；(2) 13 張卡要求的關係名與 FlowDerivation 實際產出的 12 個
邊名交集為零，其中只有 `rag-grounding`（`context_flow`）是純命名不一致。

**解法（順序是安全設計）**：
1. **Task 1 先堵洞**：端點約束（裁定採 (a)：邊的 source/target 至少一端落在
   該卡 required 節點的 backing 元件上）；假陽性回歸測試先紅後綠（`rerank`
   同名邊掛在無關端點→不得翻卡）；29 個既有 profile 測試零波及。
2. **Task 2 才開 alias**：過渡型 `core/rules/profile_relationship_alias.toml`
   僅一條 `context_flow = ["provides_retrieved_context", "prompts_llm"]`，
   loader fail-closed（key 必須是某卡的 required_relationship、value 必須是
   FlowDerivation 已知關係名）；alias 展開後的邊**同樣過端點約束**（組合有
   專屬測試釘住）。檔頭註明：UA 產出真實 `context_flow` 邊後逐條刪除，
   刪除是資料變更不是程式碼變更。
3. **Task 3 釘基線**：15 卡 status 快照測試（防止未來有人用假陽性 alias
   「修好」卡片而無人察覺）；逐張複核 15 卡裁定表；12 張卡的關係語意需求
   完整移交 Plan 16 驗收（含三個必要條件：關係名一致、端點落點、node gate 先過）。

## 四、遇到的問題與解決

1. **計畫行號漂移**：`manual_mapping_materializer.py:64-81` 實為 `:55-81`
   → Stage 1 修正計畫檔（唯一一處；其餘 19 項主張含實測數字全部吻合）。
2. **預測的測試波及沒有發生**：計畫預測拆表B會讓 graph projection 的 v1
   fixture 測試轉紅；實際該測試斷言的是結構不變式而非點亮集合，補上 v1 三條
   字彙後直接全綠，無需修 fixture。
3. **護欄盲區（review 抓到）**：Test A 只迭代 bridge 規則，`vector_db_config`
   ＋3 條 v1 字彙在盲區——TOML 搬移時漏掉任一條，測試網照樣全綠。
   → 兩層關死：Task 2 先加 39-key pin，Task 3 升級為全量 value snapshot，
   並以突變實驗證明「只有 snapshot 抓得到 valid-but-wrong 的改指」。
4. **死斷言（review 抓到）**：表A搬 TOML 後，護欄測試的「value ⊆ catalog」
   斷言永遠到不了（loader 先 raise）→ 重寫為誠實的「packaged map 能通過
   fail-closed 載入（loader 即是 enforcer）」測試並加註。
5. **`prompts_llm` alias 單側端點風險（review 提出 Important，plan-mandated）**：
   真實 FlowDerivation 地圖上兩條 alias value 只有 `prompts_llm` 能過端點
   約束、且僅靠 LLM 側端點——理論上全 RAG repo 可在無 retriever 連線證據下
   翻 `detected`。**裁定：維持計畫原定兩條 value**，理由：(1) 現有 12 個真實
   fixture 均不產出 alias 名，今日零行為變化；(2) 翻卡另需 `llm_answerer`
   自身 detected（直接 LLM 證據）的天然閘門；(3) 過渡表、刪 value 是資料
   變更；(4) 任何收緊方案都會讓機制在所有真實模板地圖上死亡，違背計畫本意。
   Final review 獨立覆核 **AGREE**，並補一個建議：第一個 full-template
   fixture 落地時釘住 `rag-grounding` 期望 status 作為誤亮偵測器——已寫入
   13.8 待裁定與 Plan 16 移交補記。
6. **architecture.md 在 gitignore 目錄**（`docs/work/Timmy/learn/` 為個人
   筆記區）→ 檔案已完整更新並通過 python 驗證（8 區塊、0 新違規、順手修
   1 個既有 ragged border），依 repo 政策不 force-add、不 commit。
7. **Plan 16 檔帶著使用者未提交的修改** → docs/work/** 的編輯一律純附加、
   不 commit、不 stage，與使用者現行未提交狀態並存（13.8.md 裁定表複核、
   Plan 16 移交清單同此原則）。
