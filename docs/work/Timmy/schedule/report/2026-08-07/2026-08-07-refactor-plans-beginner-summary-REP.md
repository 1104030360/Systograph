> 想看完整技術細節，請看同資料夾的另外五份 REP 與 PR #276。

## 先看懂三個名詞（30 秒）

| 名詞 | 白話解釋 |
|---|---|
| 端點（endpoint） | 後端開給前端呼叫的「網址」。例如 `POST /api/scans` 就是「請幫我掃描」這個動作的網址。 |
| demo 端點 | 早期為了快速展示做的「捷徑網址」。功能重複、又沒有正式路徑安全，本來就計畫要拆掉。 |
| TDD（紅綠燈開發法） | 先寫一個「現在一定會失敗的測試」（紅燈），再改程式讓它通過（綠燈）。這樣能證明測試真的有用、改動真的生效。 |

**整體在做一件事**：這個系統以前同一個功能常有「正式門」和「側門」兩條路
（demo 捷徑、舊格式 v1 的寫入路、用錯誤欄位猜位置的邏輯）。這次把所有
側門拆掉，讓每個功能只剩一條正式的路——路少了，出錯的地方就少了。

## Plan 01（Phase B）：掃描前必須先「預檢」

**問題**：掃描一個專案前，應該先看清單、決定哪些敏感檔案要不要掃
（這個步驟叫 preflight 預檢）。但舊程式留了一條「偷懶路」：不做預檢
直接掃，後端會在裡面偷偷幫你補做。兩條路並存，程式複雜又容易出錯。

**解決步驟**：
1. 先寫紅燈測試：「不帶預檢單號就掃描 → 應該收到 422 錯誤」。
   現在會失敗（因為偷懶路還在），確認測試有效。
2. 刪掉後端的偷懶路（implicit 分支），加上明確的錯誤碼
   `preflight_request_id_required`。測試轉綠。
3. 全專案有 17 個地方（測試和腳本）還在走偷懶路——寫一個共用的
   「先預檢、再掃描」小工具（`tests/helpers/web_flows.py`），
   讓 17 個地方全部改用它，以後只要維護一份。
4. 更新 API 說明文件，把「可以不帶單號」的舊敘述刪掉。

**結果**：掃描只剩「預檢 → 決定 → 掃描」一條路。審查時發現刪測試
順便刪掉了「機密值不能出現在回應裡」的檢查，已補回並實際驗證
（暫時關掉遮罩功能，確認測試真的會抓到洩漏）。

## Plan 05：拆掉會洩漏檔案路徑的載入端點

**問題**：`POST /api/viewer/load` 讓任何人丟一個「檔案路徑」給後端，
後端就直接去讀那個檔案，讀失敗還會把錯誤細節（含你電腦的路徑）
吐回去。這是一個安全漏洞（issue #140 早就記錄了）。

**解決步驟**：
1. 紅燈測試：「呼叫這個端點 → 應該收到 404（不存在）」。
2. 整個端點檔案刪除。同樣的功能保留在命令列工具
   （`systograph validate-map`）——命令列只有你本人能用，沒有網路
   暴露面，安全。
3. 建立一個「退役端點專用測試檔」（`test_retired_endpoints.py`），
   之後每拆一個端點都在這裡加測試，防止未來有人不小心加回來。
4. #140 標記為「用移除解決」，不用再花力氣做修補方案。

**結果**：漏洞根除（端點不存在就沒有洩漏問題），能力沒有消失。

## Plan 03：拆掉「一鍵建圖」demo 端點

**問題**：`POST /api/map/build` 是早期 demo 用的「跳過所有流程直接
建圖」捷徑。它繞過專案匯入、預檢等正式步驟，跟正式流程重複。

**解決步驟**：
1. 先把還在用這個捷徑「當墊腳石」的腳本改成走正式流程
   （匯入 → 掃描），確保拆掉之後腳本還能動。
2. 紅燈測試：「呼叫它 → 404」。
3. 刪掉端點和它專用的資料格式（`MapBuildApiRequest`）。
4. 清文件（API 說明有 10 處提到它）。命令列 `systograph map`
   仍提供等價功能。

**結果**：HTTP 建圖只剩正式流程一條路。過程中特別保住了一個測試——
它兼職驗證另外兩個端點，不能跟著陪葬（先改寫、等 Plan 02 再處理）。

## Plan 02（Phase B）：拆掉兩個「讀最新地圖」demo 端點

**問題**：`GET /api/map` 和 `GET /map` 回傳「整台後端最近一次建的圖」
——不管是誰的專案、哪一次掃描，就給你「最新的那份」。多專案時
可能拿到別人的圖，正式路徑（指定專案、指定建置讀取）早就存在。

**解決步驟**：
1. 紅燈測試 ×2：「兩個端點 → 404」。
2. 刪掉兩個端點（`GET /api/map/report` 保留，它是另一個還在用的
   功能）。
3. **拆彈**：所有測試腳本都拿 `GET /api/map` 當「後端活著沒」的
   探測訊號——端點一刪全部腳本會卡死。改成探測 `/openapi.json`
   （框架內建、永遠存在）。
4. 靠這些端點當墊腳石的測試，全部改走正式讀取路徑，並補上
   「讀到的圖真的有內容」的檢查（之前有測試比較「改動前後相同」，
   但如果兩邊都是錯誤畫面也會相同——這種假通過被堵起來了）。

**結果**：讀圖只剩正式路徑。注意：前端還沒改（它還會去打這兩個
404 的網址），這是計畫內接受的暫時狀況，由前端工作包 FE-2 收尾。

## Plan 08：刪掉沒人用了的舊型別和暫存槽

**問題**：上面兩個計畫完成後，`ViewerPayload` 這個包裝型別和
session 裡的「最新地圖暫存槽」就再也沒有人使用了——死程式碼留著
只會誤導後人。

**解決步驟**：
1. 全專案搜尋，確認真的沒有任何地方還在用（有的話就不能刪）。
2. 刪掉型別、暫存槽、以及順藤摸瓜找到的三處「注進去但沒人讀」的
   死接線。
3. 死碼刪除寫不出紅燈測試，安全網改用「刪除前後 1138 個測試
   結果一字不差」來證明沒有影響任何功能。

**結果**：`ViewerPayload` 在後端原始碼完全消失（grep 零命中）。

## Plan 06：移除舊格式（v1）的寫入路

**問題**：系統輸出的地圖格式已升級到 v2，但程式裡還留著一條
「緊急時可以切回去產 v1」的逃生路（三個服務、兩個分支、一個環境
變數開關）。專案還在開發期、沒有人需要這條路，留著就是複雜度。

**解決步驟**：
1. 紅燈測試：「環境變數設成 v1 → 應該直接報錯、而且不產出任何
   檔案」（舊行為是會成功產出 v1）。
2. 刪掉三個 v1 寫入服務和管線裡的分支。**注意：讀取舊 v1 檔案的
   能力完整保留**——歷史資料還是打得開。
3. 有一份「誰還在用 v1」的清冊測試（census），刪程式必須同一個
   commit 同步清冊，不然測試會擋下來（這是設計好的保險）。
4. 審查發現一個隱患：版本字串還能從建構參數傳進來、把 v2 產物
   「標籤」成 v1。修法是把版本收斂成唯一常數 `V2_SCHEMA_VERSION`。
   修的過程中全套測試又抓到「命令列會失去 v1 防呆」的回歸，
   一併補上防護和測試。

**結果**：產出只剩 v2 一條路，版本標籤不可能說謊。刪了 27 個舊
測試、新增 13 個更強的測試。

## Plan 07：畫圖的「泳道」改用正確的依據來決定

**問題**：系統地圖把元件畫在 10 條「泳道」（平面）上。以前泳道是
用 `slot`（一個舊的粗分類欄位）查表決定——slot 填錯，元件就畫錯
泳道。但系統早就有更準的欄位：`canonical_type`（元件的真實型別）。

**解決步驟**：
1. 紅燈測試：「slot 故意填錯、但 canonical_type 正確 → 泳道應該
   還是對的」。舊程式跑這個測試是紅的（畫錯道），這正是要修的病。
2. 寫一個推導器：`canonical_type → 對應的能力節點 → 節點所屬泳道`
   （對照表放在 TOML 設定檔，載入時自動驗證不能有打錯字）。
3. 換掉查表邏輯，測試轉綠。舊查表只保留給讀取歷史 v1 檔案用。
4. 用 12 個測試專案跑「改動前 vs 改動後」對照：15 個元件裡 7 個
   移到新泳道、0 個迷路，每一個移動都對照過設定檔確認合理，
   還用瀏覽器截圖前後畫面存證。

**結果**：slot 填錯不再畫錯泳道。審查另發現泳道還影響「鏡頭篩選」
（lens）功能，已補文件說明和防護測試。

## 每個計畫都走過的品管流程

```text
查核計畫 → 寫紅燈測試 → 實作(轉綠) → 獨立審查員審查
              ↑                            │
              └── 有問題就修正、再複審 ←──┘
```

外加最後一輪「整條分支」的總審查（抓跨計畫的不一致），
和一次全面驗收掃描（確認沒有殘留的舊敘述、舊符號）。
