## 1. 這個資料夾在解決什麼問題（白話版）

**現況：** KAI-Mind 掃描目標專案時，靠的是 13 條正規表示式（regex）規則，
其中 11 條只認得 Python。它能認出「這個檔案裡出現了 `QdrantClient(`」，
但**看不懂程式碼的結構**——不知道哪個檔案用了哪個檔案、哪個函式呼叫了哪個函式。

**要做的事：** 接上一個叫 **Understand-Anything（UA）** 的開源工具。
只借用它的**三支確定性腳本**，換來三樣現在完全沒有的資料：

```text
① 檔案之間的 import 關係圖    誰依賴誰
② 函式 / 類別 / export 清單    帶精確行號
③ 函式之間的呼叫關係          誰呼叫誰、第幾行
```

順帶把語言覆蓋從「幾乎只有 Python」擴到 **12 種語言**。

**不做的事：** 不用 UA 的 AI 語意分析。「這是向量資料庫」「這符合 rag-grounding
模式」這類**判斷**，從頭到尾都還是 KAI-Mind 自己的 Python 在做。

## 5. 名詞對照表（review 前先看這個）

### 5.1 這次整合的專有名詞

| 術語 | 白話 |
|------|------|
| **UA / Understand-Anything** | 一個開源程式碼理解工具。我們**只借三支腳本**，不用它的 AI 部分 |
| **sidecar** | 「側車」。把 UA 當成外部程式（Node 子行程）叫起來，不把它的程式碼併進來。好處是它壞掉不會弄壞我們 |
| **adapter** | 翻譯層。UA 講它自己的語言，adapter 把它翻成 KAI-Mind 的資料格式 |
| **call hint** | 「誰呼叫誰、第幾行」這種事實 |
| **import map** | 「哪個檔 import 哪個檔」的關係圖 |
| **Louvain / batch** | 一種自動分群演算法。把互相 import 很密集的檔案歸成一群，一群一批處理 |
| **G1 / G2 / G3** | 16E 給 UA 三個盲點的編號（函式外建構 / 工廠模式 / 外部 import） |
| **G5c** | 舊對話裡的別名，指「rag-grounding 這張卡缺 `context_flow` 邊」的問題。已正式化為 13.8 |

### 5.2 KAI-Mind 本身的名詞（讀計畫時一定會遇到）

| 術語 | 白話 |
|------|------|
| **Step 1～7** | 掃描管線的七個階段。大致是：1 匯入專案 → 2 決定掃哪些檔 → 3 收集原始事實 → 4 組成元件 → 5 推導關係 → 6 判定能力 → 7 產出檔案 |
| **ScanFact** | 掃到的一條原始事實。例如「`app.py` 用了 `QdrantClient`」 |
| **Evidence** | 那條事實的出處證明（哪個檔、第幾行、什麼規則抓到的） |
| **direct / indirect 證據** | **有精確行號** = direct（直接證據）；**只知道檔案層級、沒行號** = indirect（間接證據）。這個區分非常重要，見下一列 |
| **五態** | 每個能力節點的判定結果，只有五種：`detected`（偵測到）/ `partial`（部分）/ `undetermined`（無法判定）/ `not_detected`（確認沒有）/ `conflicted`（證據衝突）。**規則：`detected` 只認 direct 證據；只有 indirect 最多到 `partial`** |
| **52 格 / 10 planes** | 一張固定的能力參考地圖（10 個平面、52 個節點）。**不管掃到什麼都會畫出來**，掃描結果疊在上面。所以圖永遠畫得出來，差別只在有幾格被點亮 |
| **profile（15 張卡）** | 15 種 AI 系統模式，例如 `rag-grounding`（檢索接地）、`tool-calling`（工具呼叫）。每張卡有自己的達成條件 |
| **bridge** | 把 ScanFact 翻成「元件」的規則表（`component_bridge_rules.py`）。例如看到 `QdrantClient` 就產生一個「Vector Store」元件 |
| **scan_id / build_id** | `scan_id` = 一次**不可變**的掃描快照；`build_id` = 從那份快照產出一次成品。同一個 scan_id 可以產出多個 build_id |
| **Apply vs Rescan** | **Apply** = 重放同一份快照，**不重新掃**；**Rescan** = 重新掃描，產生新快照。兩者語意不同很重要 |
| **parity（對等性）** | 對比驗證：UA 掃出來的結果，和舊的 TOML 規則掃出來的，是不是一致。一致了才敢讓舊的退役 |
| **fail-closed** | 出錯就停下來，**不假裝掃完了**。相對於 fail-open（出錯還繼續，產出不完整但看起來正常） |
| **read-only 保證** | 掃描過程**絕對不寫入**被掃的專案。連暫存檔都不行 |
| **Gate-1 ～ Gate-4** | 四道驗收關卡，決定哪個計畫可以開工。定義在 [`../README.md`](../README.md) |

### 5.3 常見英文行話（文件裡沒翻譯的那些字）

這些是通用的軟體流程英文，不是這個專案發明的。文件裡保留原文是因為
程式碼與 commit 訊息也都用這些字，翻掉反而對不上。

| 英文 | 白話 | 記憶點 |
|------|------|--------|
| **cutover** | **切換**。正式把主力從舊做法換成新做法 | 像搬家：東西都準備好了，選一天正式搬過去 |
| **parity** | **對等性驗證**。新舊兩套跑出來的結果是不是一致 | 一致了，舊的才敢退休 |
| **materialization** | **物化 / 產出**。把記憶體裡的中間結果正式寫成檔案 | 從「算好了」變成「存下來了」 |
| **normalize** | **正規化**。把各種來源的資料整理成統一格式 | 統一格式才好比較 |
| **canonical** | **正規版 / 官方版**。系統認定的唯一標準版本 | 有很多草稿，但只有一份是「正式的」 |
| **sibling（檔案）** | **同層產出檔**。一次 build 產出的那一組並排檔案 | `ai_system_map.json` 和 `readiness_report.json` 是兄弟 |
| **fail-closed** | **失敗就停**。出錯時停下來，不產出半成品 | 相對於 fail-open（出錯還硬做完，看起來正常但內容不完整） |
| **fallback** | **備援 / 退路**。首選方法失敗時改用的次選方法 | |
| **preflight** | **起飛前檢查**。真正執行前先確認環境就緒 | 借用飛機起飛前的檢查表 |
| **enrichment** | **加料**。在既有資料上補欄位 | 例如檔案清單原本只有路徑，補上「語言、行數」 |
| **harness** | **測試夾具 / 測試框架**。為了跑驗證而寫的那套外圍工具 | |
| **smoke test（煙測）** | **冒煙測試**。只驗最基本的有沒有壞 | 名字來自硬體：通電看會不會冒煙 |
| **corpus** | **語料庫 / 樣本集**。拿來驗證的一批真實專案 | |
| **byte-for-byte** | **逐位元組相同**。兩個檔案完全一模一樣 | 比「內容差不多」嚴格得多 |
| **deterministic** | **確定性的**。同樣輸入永遠得到同樣輸出 | 對照組：LLM 是非確定性的 |
| **P0 / P1** | 嚴重度分級。**P0 = 最高優先**，P1 = 次高 | 在 `AGENTS.md` 裡 P1 = review 必擋 |

### 5.4 16C 特有：邊的三個等級（review 時的重點）

| 級別 | 意思 | 邊的狀態 |
|------|------|----------|
| **L1** | 真的看到「A 的程式碼呼叫了 B」，有行號 | `observed`（觀察到）　**算**卡片接線證據 |
| **L2** | 只知道「A 的檔案 import 了 B 的檔案」，沒行號 | `undetermined`（無法判定）　**不算** |
| ~~L3~~ | ~~照模板猜的~~ | 過渡期仍是 `undetermined`，由 [`16G`](./16G-retire-template-flow-derivation.md) 刪除 |

> **2026-08-04 改為兩級（選項 B）。** 原本 L2 是 `detected`、L3 是 `undetermined`；
> 模板刪掉後 `undetermined` 會沒人產生，所以把它改分配給 L2。
> 結論：**卡片要動，必須有真實呼叫點**；只有 import 關係不算數。
> L1 用 `observed` 而不是 `detected`，是為了避免跟上面那列的五態撞名。
> L2 與 L3 在過渡期都是 `undetermined`，靠 `undetermined_reason` 區分。

> **為什麼這個設計重要：** 現在的程式碼把**每一條邊都標成 `observed`**
> （`system_map_v2_normalize_service.py:153`），但那些邊其實全部來自一張寫死的
> 模板表——**宣稱「觀察到」，實際是猜的**。16C 就是要讓這個欄位變誠實。

## 6. Review 時該看什麼（給第一次 review 的人）

不用逐行讀完 2100 行。針對實作計畫（16 / 16C / 16D），看這六件事：

- [ ] **1. 硬前置擋得住嗎** — 每份計畫開頭都有「硬前置」表。
      問自己：如果前置沒做就硬幹，會發生什麼？（文件應該有寫）
- [ ] **2. Task 有驗收條件嗎** — 每個 Task 應該做得完、驗得了。
      看到「優化 XX」「改善 YY」這種沒有明確完成標準的，就是問題
- [ ] **3. 有沒有宣稱 runtime** — 這整套是**靜態分析**，
      用語必須是「static evidence suggests」，**不得**說「executed」「traversed」。
      看到宣稱實際執行過的，直接標記
- [ ] **4. 有沒有冒出信心分數** — 契約禁止 `confidence` / `score` 這類數值。
      看到就是紅旗
- [ ] **5. 有沒有超出邊界** — 最高權威是
      `ref-opensource/kai-mind-understand-anything-integration-boundary.md`。
      任何計畫跟它衝突，以它為準
- [ ] **6. 前端要不要改** — 16A 的核心論點之一是「前端契約已經夠用，資料變真就好」。
      如果某個計畫要求改前端契約，值得追問為什麼
