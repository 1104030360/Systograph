   zod）必在大 repo 掃描觸發 boundary gate 時爆——已抽離給前端（見範圍增刪）。
4. **晚做更貴（git 實測）。** `create_app()` 45 天內 3→19 參數（簽名 `web/app.py:118-136`）、

## 決策點 D1（已拍板：方案 A，2026-07-28 Timmy）

`POST /api/viewer/load` 的結果目前被無聲丟棄（A-4，與 `API-GUIDE.md:598` 明文相反）。

**裁定：方案 A** —— 實作 `SessionStore.hydrate_from_latest()`，code 對齊文件。
改動面：Protocol + 兩個實作 + `app.py`（`2.md:1193-1200` 的 Files / Produces；
`2.md:1237-1245` 是 Task 6 Step 1 的 blocking 決策點，本裁定即為其答案，可直接往下做）。

理由：
1. 保留 `API-GUIDE.md:598` 文件契約與 frontend API mode 的 load 語意，
   不把 viewer/load 降級成幾乎無作用的 endpoint。
2. 順帶解決兩實作語意分歧：`InMemorySessionStore.latest_viewer_payload()` 直接回
   `_latest_viewer_payload`（`session_store.py:121-122`，viewer/load 生效），
   `PersistentSessionStore` 卻優先回 build（`:194-198`，viewer/load 被蓋）——
  同一個 Protocol 兩種語意。方案 A 在 Protocol 層統一：重開時 hydrate 一次
   latest，之後 viewer/load 載入的 map 生效直到下一次 build。
