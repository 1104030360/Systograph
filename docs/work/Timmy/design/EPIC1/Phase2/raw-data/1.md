# 1. 你說的「組合出一個 template」要小心

你問：

> 有辦法以目前這樣一個 baseline 加上判斷出不同的 profile，組合出一個 template，讓後端可以直接插入嗎？

可以，但我不建議叫它 **template**。
比較準確應該叫：

```text
Graph Blueprint
或
Visualization Graph Composition
或
Profile Graph Fragments
```

因為 `template` 這個詞在你們 repo 目前已經比較像 `rag-core-v1` 這種 reference template。`RagTemplateService` 目前也只允許 built-in `rag-core-v1`，它會驗證 template id、system type、allowed statuses、slot id、flow references。這比較像穩定內部 reference，不適合每次掃描後動態產生一個新 template。

所以不要做：

```text
每次掃完 → 產生一個新 template → 塞資料進去
```

比較好是：

```text
每次掃完 → 產生 facts → 產生 graph projection
```

# 2. 正確分層應該長這樣

```text
Layer 1：Deterministic Facts
  掃描 repo / config / dependency / services 得到的證據

Layer 2：Canonical Readiness Map
  ai-system-map/v1

Layer 3：Profile Inference
  從 facts 判斷：
  - hybrid-rag?
  - rerank-rag?
  - corrective-rag?
  - graph-rag?
  - agentic-rag?

Layer 4：Graph Composition
  baseline graph
  + profile graph fragments
  + uncertainty / confidence overlay

Layer 5：GraphViewModel
  前端真正吃的 nodes / edges

Layer 6：Frontend Render
  畫圖、顯示 risk、evidence、confidence
```

你現在 repo 已經有 `GraphViewModel`，它包含 `nodes`、`edges`、`details`、`filters`。
而 `viewer_session_service.py` 的 `project_to_graph()` 已經明確是把 canonical facts 投影成 graph data。

所以你要擴充的是 **projection / graph composition layer**，不是每次動態產生 canonical template。

# 4. 為什麼不要「先辨識是哪一種 RAG」

因為一開始就問「是哪一種 RAG」會變成分類問題。

例如 repo 掃到：

```text
BM25Retriever
FAISS
CrossEncoderReranker
retrieval_evaluator.py
web_search_tool
citation_checker.py
```

如果你先問：

```text
這是哪一種 RAG？
```

你會卡住。
因為它同時是：

```text
legacy-v1-linear-baseline
+ hybrid-rag
+ rerank-rag
+ corrective-rag
+ agentic-rag
+ citation-grounded-rag
```

所以正確問題不是：

```text
它是哪一種 RAG？
```

而是：

```text
它有哪些 RAG capabilities？
每個 capability 有多少 evidence？
哪些 capability 會影響 readiness？
哪些 capability 應該畫在 graph 上？
```

# 5. Baseline + profile fragments 怎麼組合成視覺化 graph

可以。建議用 **graph fragments**。

## Baseline graph fragment

這是 `rag-core-v1` 產生的基礎圖：

```text
Data Sources
  ↓
Document Loader
  ↓
Chunking
  ↓
Embedding Model
  ↓
Vector Store

User Query
  ↓
App / Orchestrator
  ↓
Retriever
  ↓
Vector Store
  ↓
Prompt Builder
  ↓
LLM
  ↓
Citation / Response Composer
```

你 repo 的 `rag-core-v1.json` 目前已經定義了這些 slots 與兩條 baseline flows：`indexing` 和 `query_answer`。

---

## Hybrid RAG graph fragment

如果掃到 dense retriever + sparse retriever：

```text
Query
  ↓
Dense Retriever ─┐
                  ├→ Fusion / Merger → Reranker? → Prompt Builder
Sparse Retriever ┘
```

---

## Reranker graph fragment

如果掃到 reranker：

```text
Retriever
  ↓
Candidate Chunks
  ↓
Reranker
  ↓
Ranked Chunks
  ↓
Prompt Builder
```

---

## Corrective RAG graph fragment

如果掃到 retrieval evaluator / confidence score / fallback：

```text
Retriever
  ↓
Retrieved Chunks
  ↓
Retrieval Evaluator
  ├─ good enough → Prompt Builder
  └─ insufficient → Query Rewrite / Web Search / Second Retrieval
```

Corrective RAG 本來就是用 retrieval evaluator 評估檢索品質，再根據信心分數決定後續 retrieval action，不適合硬塞進單一線性 template。([arxiv.org](https://arxiv.org/abs/2401.15884))

---

## Graph RAG graph fragment

如果掃到 graph store / entity extraction / community summary：

```text
Documents
  ↓
Entity / Relationship Extraction
  ↓
Knowledge Graph / Graph Store
  ↓
Graph Retrieval
  ↓
Context Builder
  ↓
LLM
```

Microsoft GraphRAG 官方文件描述的是 structured hierarchical RAG，包含 knowledge graph、community hierarchy、summaries 等概念，所以它比一般 vector RAG 複雜，不應只當成 `vector_store` 的替代 slot。([microsoft.github.io][1])

# 7. 不確定的 profile 要怎麼畫

這點很重要。

不是所有 profile 都是 confirmed。
所以前端 graph 要表達 confidence。

我建議：

| Profile 狀態     | 視覺化方式                          | Gate 影響                              |
| -------------- | ------------------------------ | ------------------------------------ |
| `confirmed`    | 實線 node / edge                 | 可以影響 readiness                       |
| `likely`       | 虛線 node / edge，顯示「likely」badge | 主要給 warning / recommended next check |
| `weak_signal`  | 淡色 ghost node，預設可摺疊            | 不直接 fail                             |
| `not_detected` | 不顯示，或只在 advanced view 顯示       | 不影響 gate                             |

例如：

```text
Retrieval Evaluator [likely]
```

代表：

```text
有一些證據像 corrective RAG，
但還不足以 confirmed。
```

這樣使用者不會被誤導，以為 Systograph 100% 還原了架構。

# 8. 後端資料流應該怎麼設計

你可以想成四個 service：

```text
1. EvidenceCollector
2. BaselineMapper
3. ProfileInferenceService
4. GraphCompositionService
```

## 1. EvidenceCollector

負責掃 repo，抽 deterministic facts。

```json
{
  "id": "evidence:bm25-retriever",
  "kind": "code_symbol",
  "file": "src/retrieval.py",
  "symbol": "BM25Retriever",
  "line_start": 42
}
```

---

## 2. BaselineMapper

把 facts 放進 `ai-system-map/v1` 的基本 slots。

例如：

```json
{
  "slot": "retriever",
  "status": "detected",
  "instances": [
    {
      "id": "component:retriever:bm25",
      "kind": "retriever",
      "name": "BM25Retriever",
      "evidence_ids": ["evidence:bm25-retriever"]
    }
  ]
}
```

目前 `ai-system-map/v1` 的 `components_by_slot`、`evidence`、`flows`、`extensions`、`unmapped_components`、`risk_hints` 已經能支撐這種模式。

---

## 3. ProfileInferenceService

從 evidence 判斷有哪些 profile。

```json
{
  "profile_id": "hybrid-rag",
  "status": "confirmed",
  "confidence": 0.91,
  "evidence_ids": [
    "evidence:bm25-retriever",
    "evidence:vector-store"
  ]
}
```

---

## 4. GraphCompositionService

根據：

```text
baseline graph
+ detected profiles
+ evidence
+ risk hints
```

產出：

```text
GraphViewModel
```

而不是產出新的 `rag-template-vX.json`。

# 9. 你現在說的流程，應該修成這樣

你原本說：

```text
掃完後
→ 先辨識出是哪一種 RAG
→ 組合出一個 template
→ 根據 deterministic layer 證據放入 slot
→ 做出 graph model
→ 前端渲染
```

我建議改成：

```text
掃完後
→ 先產生 deterministic evidence
→ legacy v1 linear baseline slot mapping 到 ai-system-map/v1
→ 根據 evidence 推論多個 profiles
→ 根據 profiles 選用 graph fragments
→ graph fragments + baseline map 組合成 GraphViewModel
→ 前端渲染
```

差別在這裡：

| 你原本想法          | 建議修正                                                       |
| -------------- | ---------------------------------------------------------- |
| 先辨識是哪一種 RAG    | 先掃 evidence，再推論多個 profiles                                 |
| 組合出 template   | 組合出 visualization graph / graph fragments                  |
| 把證據放入 slot     | legacy v1 linear baseline slots 放核心證據，profile nodes 用 extensions / overlays |
| 做出 graph model | 從 canonical map + profile fragments 投影成 GraphViewModel     |
| 前端渲染           | 正確，這段保留                                                    |

# 10. 為什麼不能把所有 profile 都塞進 slot

因為 slot 是 readiness contract 的一部分。
如果你每新增一個 profile 就新增一堆 slot，`ai-system-map/v1` 會變得很不穩定。

例如你如果為 Corrective RAG 加：

```text
retrieval_evaluator
fallback_retriever
query_rewriter
web_search
```

又為 Graph RAG 加：

```text
entity_extractor
relationship_extractor
graph_store
community_summarizer
```

又為 Agentic RAG 加：

```text
agent
tool_registry
tool_policy
approval_gate
```

最後 `rag-core-v1` 會變大雜燴。

比較好是：

```text
核心 RAG 元件 → 放 legacy v1 linear baseline slots
進階能力元件 → 放 extensions / graph overlay / future topology layer
```

# 11. 目前 repo 的限制

目前 `flow_derivation_service.py` 是依照 template 的 `slot_order` 建立相鄰 slot pairs，而且只有兩端 slot 都 detected 才建立 edge；每個 slot 目前只取排序後第一個 component instance。

這代表目前的 flow derivation 比較適合：

```text
baseline RAG 線性流程
```

不適合直接表達：

```text
hybrid retrieval fan-out / fan-in
corrective branch
graph retrieval branch
agent tool loop
```

所以如果要做 profile 組合圖，你不應該只改 `rag-core-v1 slot_order`。
你應該新增一個 graph composition layer。

# 13. 最後一句話

你現在該做的不是：

```text
辨識 RAG 類型 → 動態組 template → 塞 slot
```

而是：

```text
掃 evidence → 填 baseline map → 推論多個 profiles → 組 graph fragments → 產生 GraphViewModel
```

也就是：

```text
template 不要動態生成；
graph 可以動態組合。
```

這樣才能同時做到：

* 使用者不用手動選。
* baseline contract 穩定。
* 多 profile 可以共存。
* 前端可以畫出更貼近真實架構的圖。
* 不會讓 `rag-core-v1` 變成不可維護的大雜燴。
