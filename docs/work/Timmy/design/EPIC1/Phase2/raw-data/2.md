今天是 **2026-06-24**。

## 直接結論

這 12 種 RAG **都有共同 base 架構**，但這個 base 不能理解成「同一條固定線性 template」。
比較準確是：

```text
所有 RAG 都共享一個 RAG Kernel / RAG Readiness Base：
資料來源 → 建索引 / 表徵 → 查詢 → 檢索 → 組上下文 → LLM 生成 → 回答 / 引用 / 評估
```

但它們的差異在於：

```text
有些改 indexing
有些改 retrieval
有些改 reranking
有些改 query control
有些改 self-check
有些改 knowledge store
有些改 modality
有些改 agent orchestration
```

所以 Systograph 不應該為 12 種都做 12 個互斥 template。
應該做：

```text
一個共同 base readiness contract
+
多個 profile graph fragments / checksets
```

---

# 1. 共同 base 架構長什麼樣子

我建議你把所有 RAG 的共同 base 定義成這個：

```text
Data Sources
  ↓
Ingestion / Loading
  ↓
Preprocessing / Chunking / Structuring
  ↓
Representation / Indexing
  ↓
Knowledge Store
  ↓
Query / Task Input
  ↓
Retrieval / Selection
  ↓
Context Assembly
  ↓
LLM / Generator
  ↓
Answer / Citation / Evaluation
```

這個比你現在 `rag-core-v1` 更抽象一點。
因為 `rag-core-v1` 比較偏傳統 textual vector RAG：

```text
data_sources
document_loader
chunking
embedding_model
vector_store
retriever
prompt_builder
llm
citation_or_response_composer
```

這對 legacy v1 linear baseline 很合理，但對 GraphRAG、RAPTOR、Multimodal RAG、MRAG 會太窄。你 repo 目前 `rag-core-v1.json` 確實是用這種 baseline RAG slots。

所以真正可跨 12 類使用的 base 應該稍微泛化：

| 現在 `rag-core-v1` slot | 建議抽象化名稱                        | 為什麼                                                                           |
| --------------------- | ------------------------------ | ----------------------------------------------------------------------------- |
| `chunking`            | `preprocessing_or_structuring` | GraphRAG 不只是 chunk，還有 entity / relationship extraction                        |
| `embedding_model`     | `representation_model`         | MRAG 可能用 multi-head activation；Multimodal RAG 可能用 image/table/formula encoder |
| `vector_store`        | `knowledge_store`              | 可能是 vector DB、BM25 index、graph store、tree index、multimodal graph              |
| `retriever`           | `retrieval_or_selection`       | Self-RAG / Agentic RAG 可能由模型或 agent 決定何時 retrieve                             |
| `prompt_builder`      | `context_assembler`            | GraphRAG / RAPTOR / Multimodal RAG 的 context 組裝不一定是單純 prompt template         |

# 2. 12 種 RAG 是否共享 base？

答案是：**都有，但共享的是 abstract base，不是完全一樣的 topology。**

|  # | RAG 類型                           | 是否有共同 base？                            | 它主要改哪一段                                                     |
| -: | -------------------------------- | -------------------------------------- | ----------------------------------------------------------- |
|  1 | Naive / 2-Step RAG               | 有，最標準                                  | 幾乎就是 base 本身                                                |
|  2 | Advanced RAG                     | 有                                      | query transformation、reranking、recursive retrieval          |
|  3 | Hybrid RAG                       | 有                                      | retrieval 多路並行，BM25 + dense                                 |
|  4 | Corrective RAG / CRAG            | 有                                      | retrieval evaluator + fallback / corrective action          |
|  5 | Self-RAG                         | 有，但 retrieval 由模型動態決定                  | retrieve / generate / critique loop                         |
|  6 | Agentic RAG                      | 有，但 retrieval 被包成 tool                 | agent 決定何時 retrieve                                         |
|  7 | GraphRAG                         | 有，但 knowledge store 不是單純 vector store  | knowledge graph、community summary                           |
|  8 | Tree / Hierarchical RAG          | 有，但 index 是 tree / hierarchy           | recursive summary tree                                      |
|  9 | Contextual Retrieval RAG         | 有                                      | chunk 前補 context，改善 indexing / retrieval                    |
| 10 | Multimodal / Semi-structured RAG | 有，但資料與表示法更多元                           | image、table、formula、text cross-modal retrieval              |
| 11 | Modular RAG                      | 有，而且它本身就是把 base 拆模組                    | 用來替換不同 RAG 模組                                               |
| 12 | Multi-Head RAG / MRAG            | 有，但 representation / retrieval key 很特殊 | 用 multi-head attention activations 做 multi-aspect retrieval |

# 3. 每一種對 base 的「差異點」

## 1. Naive / 2-Step RAG

這個就是最標準的 base。

LangChain 官方 RAG 教學把流程拆成：

```text
1. Indexing
2. Retrieval and generation
```

並且明確說 indexing 是 ingest / index data，runtime 則是 retrieve relevant data from index，再傳給 model。([LangChain 文檔][1])

所以 legacy v1 linear baseline 可以直接用：

```text
legacy-v1-linear-baseline profile
```

---

## 2. Advanced RAG

Advanced RAG 不是一個單一固定架構，比較像「在 baseline 上加強 retrieval」。

LlamaIndex 官方 Advanced Retrieval Strategies 包含：

* reranking
* recursive retrieval
* embedded tables
* small-to-big retrieval
* query transformations
* composable retrievers

這表示 Advanced RAG 其實是多個 profile 的集合，不是一個乾淨單一 template。([Developer Documentation][2])

對 Systograph 來說應該拆成：

```text
query-transform profile
reranker profile
recursive-retrieval profile
table-retrieval profile
```

不要只做一個叫 `advanced-rag-template` 的東西。

---

## 3. Hybrid RAG

Hybrid RAG 共享 base，但改的是 retrieval。

Haystack 官方說 hybrid retrieval 是把 sparse 和 dense retriever 放在同一個 pipeline，兩邊都 fetch candidate documents，再 combine 成 final ranking。([Haystack 文檔][3])

它的 fragment 是：

```text
Query
  ↓
Dense Retriever ─┐
                  ├→ Join / Fusion → Top Documents
Sparse Retriever ┘
```

所以它不是新 base，而是：

```text
legacy-v1-linear-baseline
+ hybrid-retrieval profile
```

---

## 4. Corrective RAG / CRAG

CRAG 共享 base，但加了 retrieval evaluator。

CRAG repo README 說它設計 lightweight retrieval evaluator 來評估 retrieved documents 品質，根據 confidence degree 觸發不同 retrieval actions，並可用 web search 擴充結果；它也明確說 CRAG 是 plug-and-play，可接到各種 RAG-based approaches。([GitHub][4])

所以它非常適合 Systograph 的 profile stack：

```text
legacy-v1-linear-baseline
+ corrective-rag profile
+ maybe external-search profile
```

不是單獨一個獨立 template。

---

## 5. Self-RAG

Self-RAG 共享 base，但 retrieval 不是固定每次都做。

Self-RAG 官方 repo 說它會學會 retrieve、generate、critique；跟廣泛採用的 RAG 不同，Self-RAG 可以 on demand retrieve，甚至完全 skip retrieval，也可以多次 retrieve，並用 reflection tokens 批判自己的 generation。([GitHub][5])

所以 Self-RAG 不能用固定線性圖表示成：

```text
Query → Retriever → LLM
```

比較像：

```text
LLM decides:
  retrieve?
  generate?
  critique?
  retrieve again?
```

但它仍然有 RAG base，只是 retrieval control 變成動態。

---

## 6. Agentic RAG

Agentic RAG 共享 base，但 retriever 變成 agent tool。

LangChain 官方 RAG agent 範例就是讓 agent 使用 retrieval tool；同一頁也同時展示 RAG agent 和 two-step RAG chain。([LangChain 文檔][1])

所以 Agentic RAG 是：

```text
legacy-v1-linear-baseline
+ agent-controller profile
+ retrieval-tool profile
+ tool-risk profile
```

對 Systograph 來說，Agentic RAG 不只是 RAG quality 問題，還會牽涉：

* tool permission
* tool call log
* human approval
* external API exposure
* data leaves device

這應該進 Agent Tool Risk Check，而不是硬塞進 RAG template。

---

## 7. GraphRAG

GraphRAG 共享 base，但 knowledge store / retrieval path 大幅不同。

Microsoft GraphRAG 官方文件把 GraphRAG 描述成 structured hierarchical RAG，會從 raw text 建 knowledge graph、community hierarchy、community summaries，再用 global / local / DRIFT / basic search 等方式查詢。([arXiv][6])
另外 Microsoft GraphRAG 官方文件也強調 structured hierarchical RAG 與 community summaries。([Anthropic][7])

GraphRAG 的 base 不是：

```text
chunk → embedding → vector store
```

而比較像：

```text
documents
  ↓
entity / relationship extraction
  ↓
knowledge graph
  ↓
community summary
  ↓
graph retrieval
  ↓
context assembly
  ↓
LLM
```

所以 GraphRAG 應該是：

```text
legacy-v1-linear-baseline-compatible
+ graph-knowledge profile
+ graph-retrieval fragment
```

但不能只把 `vector_store` 改名成 `graph_store` 就結束。

---

## 8. Tree / Hierarchical RAG

RAPTOR 共享 base，但 indexing 變成 tree index。

RAPTOR 論文說它會 recursively embed、cluster、summarize chunks，從 bottom-up 建 tree，在 inference 時從 tree retrieve，整合不同抽象層級的資訊。([arXiv][6])

所以它是：

```text
legacy-v1-linear-baseline
+ hierarchical-index profile
+ recursive-summary profile
```

它和 GraphRAG 有點像，都是改 knowledge organization，但一個偏 graph/community，一個偏 tree/summary hierarchy。

---

## 9. Contextual Retrieval RAG

Contextual Retrieval 共享 base，而且是最明顯的 indexing-side profile。

Anthropic 官方文章說傳統 RAG 會先把 corpus 切 chunks、embedding、存 vector DB；Contextual Retrieval 則是在 chunk 前補上 chunk-specific explanatory context，再做 embedding 和 BM25 index。([Anthropic][7])

所以它不是新拓樸，而是：

```text
legacy-v1-linear-baseline
+ contextual-chunking profile
+ maybe contextual-BM25 profile
```

Anthropic 也說 contextual embeddings + contextual BM25 + reranking 可以疊加，這剛好支持我們前面講的「profile 可疊加」。([Anthropic][7])

---

## 10. Multimodal / Semi-structured RAG

Multimodal RAG 共享 base，但資料型態、representation、retrieval 都變多模態。

RAG-Anything 論文描述的是 unified framework for multimodal content，包括 text、visual elements、structured tables、mathematical expressions，並用 dual-graph construction 捕捉 cross-modal relationships 和 textual semantics。([arXiv][8])

所以這種不適合只用：

```text
document_loader → chunking → embedding_model
```

要泛化成：

```text
modality parser
multimodal representation
cross-modal retrieval
evidence assembler
```

但仍然屬於：

```text
data → representation/index → retrieval → generation
```

---

## 11. Modular RAG

Modular RAG 是最明顯支持我們架構設計的類型。

RAGLAB README 說它是 modular, research-oriented unified framework，支援 RAG pipeline from data collection and training to auto-evaluation，並 reproduces 6 RAG algorithms。([GitHub][9])

這代表 Modular RAG 本身就不是一種單一 topology，而是把 RAG 拆成可替換模組。
所以它應該對應 Systograph 的：

```text
profile composition
checkset composition
module capability detection
```

---

## 12. Multi-Head RAG / MRAG

MRAG 共享 base，但改的是 representation / retrieval key。

MRAG 官方 repo 說它針對 multi-aspect queries，使用 Transformer multi-head attention layer activations，而不是 decoder layer，作為 fetching multi-aspect documents 的 keys。([GitHub][10])
MRAG 論文摘要也說它可以整合到既有 RAG frameworks 和 benchmarking tools。([arXiv][11])

所以 MRAG 不是完全新 pipeline。它是：

```text
legacy-v1-linear-baseline
+ multi-aspect-retrieval profile
+ model-internal-representation profile
```

但這個 profile 對 Systograph 來說比較難掃，因為 evidence 可能藏在 model code 或 activation extraction code，不像 BM25 / reranker 那麼容易用 dependency 或 class name 掃到。

---

# 4. 對 Systograph 的結論

## 這 12 類可以共用一個 base，但 base 要抽象化

我建議 Systograph 把 base 從：

```text
legacy v1 linear baseline slots
```

升級概念成：

```text
RAG Readiness Kernel
```

建議 base contract：

```text
1. data_sources
2. ingestion
3. preprocessing_or_structuring
4. representation_builder
5. knowledge_store
6. query_entrypoint
7. retrieval_controller
8. retriever_or_selector
9. context_assembler
10. generator_llm
11. response_composer
12. grounding_or_citation
13. evaluation_or_observability
```

這個 base 可以容納 12 種 RAG。
但現階段 repo 不一定要馬上改 schema，因為你目前 `ai-system-map/v1` 已經穩定，且 `RagSystemMap` 內有 `extensions`、`unmapped_components`、`risk_hints` 等欄位，可以先承接進階訊號。

# 5. 12 種 RAG 對應的 profile fragments

| RAG 類型               | 建議 Systograph profile      | Graph fragment                                              |
| -------------------- | ------------------------ | ----------------------------------------------------------- |
| legacy v1 linear baseline            | `legacy-v1-linear-baseline`           | linear retrieval-generation                                 |
| Advanced RAG         | `advanced-retrieval`     | query transform / recursive retrieval / rerank              |
| Hybrid RAG           | `hybrid-retrieval`       | dense + sparse → fusion                                     |
| CRAG                 | `corrective-retrieval`   | retriever → evaluator → fallback                            |
| Self-RAG             | `self-reflective-rag`    | retrieve / generate / critique loop                         |
| Agentic RAG          | `agentic-rag`            | agent → retrieval tool                                      |
| GraphRAG             | `graph-knowledge-rag`    | entity / relation → graph store → graph retrieval           |
| RAPTOR               | `hierarchical-rag`       | chunks → recursive summaries → tree retrieval               |
| Contextual Retrieval | `contextual-indexing`    | chunk → contextualizer → embedding/BM25                     |
| Multimodal RAG       | `multimodal-rag`         | modality parsers → multimodal store → cross-modal retrieval |
| Modular RAG          | `modular-rag`            | swappable modules / pipeline graph                          |
| MRAG                 | `multi-aspect-retrieval` | multi-head activations → multi-aspect retrieval             |

# 6. 最重要的產品設計判斷

## 不要問：

```text
這個 repo 是哪一種 RAG？
```

## 要問：

```text
這個 repo 命中了哪些 RAG capabilities？
每個 capability 有哪些 evidence？
這些 capability 對 readiness 有什麼風險？
哪些 fragment 要畫在 GraphViewModel？
```

這樣你就可以處理：

```text
Contextual Retrieval + Hybrid RAG + Reranker + CRAG
```

或：

```text
GraphRAG + Agentic RAG + Multimodal RAG
```

這種混合型系統。

# 7. 最後修正版流程

```text
Import Repo
  ↓
Deterministic Evidence Scan
  ↓
legacy v1 linear baseline Readiness Mapping
  ↓
Capability Signal Detection
  ↓
Multi-profile Inference
  ↓
Profile Checkset Composition
  ↓
Graph Fragment Composition
  ↓
GraphViewModel
  ↓
Unified Readiness Report
```

一句話：

> **12 種 RAG 都有共同 base，但共同的是 abstract RAG readiness kernel，不是同一個固定 visual template。Systograph 應該用 baseline contract 承接共同部分，用 profiles / graph fragments 承接變體差異。**
